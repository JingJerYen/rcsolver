# rcsolver 規劃（v1）

已決定：AR 做到「相機預覽 + 箭頭引導 + 轉到位按一下拍」這一級、每面一張共 6 張、4x4～7x7 自寫 reduction 求解器、手動修正是 MVP、部署 Cloudflare Workers（Node 也能跑）、先用 Opus 5.5 做準確率實驗、前後端同一 repo、繁中介面。

里程碑 0 已完成（實驗頁 + `/api/recognize`，真實照片 2×2 與 4×4 全對）。里程碑 1 已完成：3×3 辨色 → 合法性檢查 → min2phase 求解 → 3D 動畫逐步引導。UI 原則：幾乎不用文字，圖示為主，連 3 歲小孩也能照著做。2×2（IDA*，最佳解）與 4×4（中心 BFS 表 → 翼塊 3-循環配對 → OLL/PLL parity → min2phase，約 120 步）也已完成，每一段都在模擬器上驗證。5×5～7×7 也完成了（`web/src/solvers/solveN.ts`）：中心依軌道分三階段用離線算好的距離表下降（奇數階以固定中心為座標系，中層轉動視為整顆旋轉）；翼塊每個軌道用外層 setup + 3-循環公式放到「參考」的位置（奇數階參考中央邊塊，偶數階參考最外軌道），奇排列先用純翻邊公式修正；偶數階最後做 OLL/PLL parity（把所有內層一起轉的 4×4 公式）；再當 3×3 解。步數約 5×5 280、6×6 480、7×7 750，手機上一兩秒。導覽模式已完成：求解器回報每一段的用途（`segments`），頁面顯示階段籤、只把該段處理的格子留彩色（其餘純灰）、「?」展開策略說明；2×2 標為最短解，3×3 分成 Kociemba 的兩個階段。3×3 教學模式已完成（`web/src/solvers/lbl3.ts`：層先法，白底黃頂，右手公式／左右插入／十字公式／Sune／A 公式／U 公式，每塊一段說明與公式重播；入口是核對畫面的畢業帽，只有 3×3 出現）。2×2 與大方塊的教學版尚未做。下一步：縮短步數（更好的 3-循環選擇、中心階段合併）、實機拍 5×5 驗證辨色。

目標：手機網頁版魔術方塊求解器，支援 2x2 到 7x7。使用者拍下方塊 → 後端轉交 Claude 辨色 → 前端建立初始狀態 → 前端求解 → 以 3D 動畫（參考「四乘四・照片換角解法」頁的互動形式）一步一步引導轉動。

架構沿用 idiom-guess 的做法：**靜態前端 + 一個很薄的後端**，後端只做一件事（收圖 → Claude → 回辨色結果），並負責限流、每日額度與用量記錄。

---

## 1. 整體流程

```
[1 拍攝]  相機引導 → 抽幀/挑清晰幀/透視校正/壓縮（OpenCV.js，全在瀏覽器）
   ↓ 上傳 6 張（每面一張）壓縮後的小圖，不上傳影片
[2 辨色]  POST /api/recognize → Claude Vision → 每面 N×N 顏色矩陣 + 每格信心值
   ↓
[3 核對]  前端畫出展開圖（net），用計數與合法性檢查標出可疑格，使用者可點選修正  ← MVP 必要
   ↓
[4 求解]  全在瀏覽器：2x2 自寫搜尋、3x3 用 min2phase/cubejs、4x4~7x7 自寫 reduction 求解器
   ↓ 求解後先在內部模型模擬整段公式，確認能回到復原狀態才顯示
[5 引導]  3D 動畫逐步示範（上一步／下一步／自動播放／速度／層數指示條／公式進度）
```

## 2. 前端（手機瀏覽器）

| 模組 | 內容 | 技術 |
|---|---|---|
| 拍攝 | 取景框引導、固定拿法順序拍 6 面（例如 U→F→R→B→L→D，每拍一面提示怎麼轉），抽幀挑最清晰的一張，偵測方塊正方形並做透視校正，縮到約 512px 後以 JPEG 上傳 | getUserMedia、OpenCV.js |
| 核對 | 展開圖顯示辨識結果，可疑格高亮，點格子循環換色；每色格數必須等於 N² | 自寫 |
| 求解 | 見第 4 節 | TypeScript |
| 動畫引導 | 沿用參考頁的 UI：大字公式、層數指示條（N 格）、順逆時針說明、上一步／下一步／自動播放／速度、拖曳換視角、標準／背面／頂面視角按鈕、公式 token 進度 | 第一版可直接把參考頁的 Canvas 2D 渲染器一般化到 N 層；之後要做 AR 疊加時再換 Three.js |
| 隱私說明 | 拍攝畫面前明確告知「照片會上傳到雲端辨識，不會保存」 | UI 文案 |

AR 的程度分三級（見第 7 節問題 1）：
- **A. 引導拍攝 + 畫面旁 3D 示範**：不追蹤方塊，手機各家瀏覽器都能跑。建議先做這級。
- **B. 相機畫面上疊箭頭**：需要即時追蹤方塊姿態。iOS Safari 沒有 WebXR AR，只能用相機畫面 + 自己做追蹤（OpenCV.js 找色塊格線）。難度高很多，準確率不穩。
- **C. WebXR**：Android Chrome 可，iPhone 不行。不建議當目標。

## 3. 後端（唯一一個模型端點）

與 idiom-guess 相同的骨架（TypeScript、zod 驗證、`callJson` 式的「呼叫 → 驗 schema → 重試一次」、MOCK 模式、結構化 log），但只有一個端點：

```
POST /api/recognize
  body: { size: 2..7, faces: [{ face: "U", image: <base64 jpeg> } ×6 ] }
  limit: 每張 ≤ 300KB，總量 ≤ 2MB
  resp: { ok, faces: { U: [[...]], F: ..., }, confidence: {...}, warnings: [...] }
GET  /api/health
```

- 6 張圖**一次**送給 Claude（同一個請求），讓模型能跨面比對顏色（橘／紅、白／黃在暖光下最容易混）。
- 要求模型輸出 JSON：每面 N×N 的顏色代號 + 每格信心值 + 它認為可疑的格子；後端用 zod 驗格式、驗每色數量 = N²。
- 影像只在記憶體中轉交，不落地、不記 log；只記 token 用量與耗時。
- 限流：每 IP 每分鐘（express-rate-limit 或平台的 rate limit）、**每日全站上限**（超過就回 503 + 訊息），兩者都用環境變數設定。
- 模型：先用 `claude-opus-5-5` 做準確率實驗（6 張 512px 圖約 8–9k input tokens，一次約 US$0.04）；再比較 `claude-sonnet-5-5`（約 $0.02）與 `claude-haiku-5-5`（約 $0.001），由準確率決定。

部署選項（見問題 5）：
- **Cloudflare Workers + Static Assets**：前後端一個專案、免費額度大、沒有休眠；限流可用 Workers Rate Limiting，每日額度用 KV。Anthropic SDK 走 fetch，可在 Workers 跑。
- **Render**（idiom-guess 現在的做法）：程式碼幾乎可直接搬，但免費方案閒置會休眠，第一次開要等 30 秒以上。

## 4. 求解器（全在瀏覽器）

| 尺寸 | 方案 | 備註 |
|---|---|---|
| 2x2 | 自寫 IDA*（狀態數 3.67M，瀏覽器可在 1 秒內解） | 最佳解 ≤ 11 步 |
| 3x3 | min2phase.js 或 cubejs（Kociemba 兩階段） | 約 20 步；可用其 verify 檢查狀態合法 |
| 4x4–7x7 | **自寫 reduction 求解器**（已完成）：中心 → 邊塊配對 → 當 3x3 解 → 偶數階 parity 修正 | 非最佳解，4x4 約 120 步、5x5 約 280、6x6 約 480、7x7 約 750，對「跟著轉」的用途可接受。中心距離表離線產生（`npm run gen:tables`），頁面按尺寸抓取 |

每段求解都在內部方塊模型上模擬一遍，確認最後回到復原才輸出（參考頁的 `isSolved` 斷言就是這個做法）。

替代方案（不建議，違反薄後端）：後端跑現成的 Python / C++ NxN 求解器，需要大查表與常駐機器。

## 5. 辨色準確率策略（最大風險）

1. **拍攝端先把題目變簡單**：固定拿法、取景框、透視校正成正方形、固定尺寸。這比換模型有效。
2. **一次送 6 面**讓模型跨面校色，並回報信心值。
3. **後端硬性檢查**：每色 N² 格；3x3 可直接驗合法性；NxN 則在求解時若 reduction 卡住，回報「請檢查」。
4. **使用者修正 UI** 是 MVP 必備：任何辨識錯都能手動改，否則無法往下走。
5. **里程碑 0 = 準確率實驗**：先做一頁「上傳 6 張照片 → 看辨識結果」的實驗頁，用真實照片（不同光線、不同品牌方塊）量測，至少 20 組，再決定模型與是否需要 OpenCV 預處理。

## 7. 待釐清的問題

1. **AR 要做到哪一級？** 建議先做 A（引導拍攝 + 畫面旁 3D 示範）。B（相機畫面上疊箭頭）要即時追蹤方塊，iPhone 又沒有 WebXR，風險高。
2. **拍攝方式**：每面一張（6 張，按固定順序）還是角落照 2 張（每張看到 3 面）？建議 6 張，辨識較穩；偶數階方塊沒有固定中心，面的方向完全靠拍攝順序決定，更需要固定拿法。
3. **4x4～7x7 求解器自己寫**（純前端、非最佳解）可以接受嗎？
4. **手動修正 UI 列為 MVP** 可以嗎？
5. **部署平台**：Cloudflare Workers（建議）還是 Render（跟 idiom-guess 一樣）？
6. **模型與成本**：先用 Opus 5.5 做實驗，再依準確率決定要不要降到 Sonnet / Haiku？
7. **用量控管**：每日全站上限要設多少？要不要像私人工具一樣加一個簡單的 access code，還是像 idiom-guess 完全公開？
8. **配色**：不同品牌方塊配色不同（參考頁是白上橘前、綠右）。建議不寫死，從辨識到的中心（奇數階）或拍攝順序（偶數階）推出相對關係。要支援非標準配色（例如黑底／無白色）嗎？
9. **Repo 結構**：前後端放同一個 repo（跟 idiom-guess 一樣）？
10. **介面語言**：繁體中文為主？要不要同時有英文？
